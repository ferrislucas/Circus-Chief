# FRD: Add Model Button Fails for Providers on Non-Secure Origins

| Field | Value |
|---|---|
| Status | Proposed |
| Date | 2026-08-15 |
| Type | Bug fix / Functional requirement |
| Affected area | Providers — ProviderForm / ProviderModelsList |
| Severity | High (blocks core workflow for third-party providers) |

---

## 1. Background

Circus Chief lets users configure third-party providers (Anthropic-compatible endpoints, OpenAI/Codex, Google Gemini) and register models against them. When creating a third-party provider, the user must add at least one model via the **"+ Add Model"** button in the provider form modal.

Users report that clicking **"+ Add Model"** does nothing when editing or creating a third-party provider. No row appears, no error is surfaced.

## 2. Problem Statement

The "+ Add Model" button is non-functional whenever the web app is served over plain HTTP from a non-localhost origin (e.g. LAN IP `http://192.168.86.28:5001`). Since Circus Chief is a **local-first** app commonly accessed from other machines on a network (browser on a laptop, server on another box), this is a primary supported access pattern, not an edge case.

The failure is silent: the handler throws, the row is never pushed to local state, and the UI gives no feedback. Users conclude the feature is broken.

## 3. Root Cause

`packages/web/src/composables/useProviderForm.js` — `addLocalModel()`:

```js
localModels.value.push({
  _localKey: crypto.randomUUID(),  // ← throws on insecure origins
  modelId: '',
  ...
});
```

`crypto.randomUUID()` is defined **only in secure contexts** (HTTPS, or `localhost` / `127.0.0.1`). On `http://<lan-ip>:port`, `window.isSecureContext === false` and `crypto.randomUUID` is `undefined`. The click handler throws `TypeError: crypto.randomUUID is not a function`; `localModels.push()` never executes.

### Verified reproduction

| Origin | `typeof crypto.randomUUID` | Result of clicking "+ Add Model" |
|---|---|---|
| `http://localhost:5001/settings/providers` | `"function"` | Model row appears ✅ |
| `http://192.168.86.28:5001/settings/providers` | `"undefined"` | `TypeError`; list stays "No models added yet." ❌ |

### Why it presents as third-party-specific

The bug also affects the built-in provider "Settings" modal, but built-in providers ship with models pre-populated, so "+ Add Model" is rarely exercised there. Third-party providers start with an **empty** model list — adding a model is mandatory, so the bug always surfaces there.

### Why it was not caught

- **Unit tests**: jsdom/Node expose `crypto.randomUUID` unconditionally.
- **E2E tests**: the Playwright suite always targets `localhost` (via `./scripts/pw.sh`), which is a secure context.

Introduced by `3ed3390e` (provider model management), which switched `v-for` keys from array index to a client-generated `_localKey`.

## 4. Scope

**In scope**
- The "+ Add Model" action in `ProviderModelsList` / `useProviderForm`.
- Any other call site relying on `crypto.randomUUID` for non-security identifiers.
- Regression test coverage for insecure-origin execution.

**Out of scope**
- Serving the app over HTTPS (separate infrastructure work).
- Any change to model persistence, reconciliation, or tier semantics.

## 5. Functional Requirements

### FR-1 — Add Model works on all supported origins
Clicking "+ Add Model" SHALL append an editable, empty model row on any origin the app is reachable from, including plain-HTTP non-localhost origins (secure context: `false`).

### FR-2 — Stable client-side keys without secure-context APIs
Each locally added (unsaved) model row SHALL receive a client-side key that is:
- unique among rows in the current form session;
- stable across reordering, so `v-for` moves DOM nodes with their data instead of patching in place (the original reason for `_localKey`);
- generated **without** requiring `crypto.randomUUID`. A non-crypto fallback (timestamp + `Math.random` counter) is acceptable because the key is a UI identity, not a security token.

### FR-3 — No silent failures
If model-row creation fails for any reason, the UI SHALL surface an error (existing `error` ref / toast) rather than failing silently.

### FR-4 — Shared helper
Key generation SHALL live in a single shared utility (e.g. `packages/web/src/utils/id.js`) so future call sites cannot reintroduce the secure-context dependency. Suggested shape:

```js
export function localId(prefix = 'local') {
  if (typeof crypto !== 'undefined' && typeof crypto.randomUUID === 'function') {
    return crypto.randomUUID();
  }
  return `${prefix}-${Date.now()}-${Math.random().toString(36).slice(2)}`;
}
```

### FR-5 — No behavioral change on secure origins
On `localhost`/HTTPS, behavior SHALL be unchanged (UUID keys still used where available).

## 6. Acceptance Criteria

- [ ] On `http://<lan-ip>:5001/settings/providers`, editing a third-party provider and clicking "+ Add Model" appends a row.
- [ ] A newly created third-party provider can have a model added, tier selected, and saved; the model persists after reload.
- [ ] Reordering two unsaved rows moves focus/DOM nodes correctly (existing `_localKey` behavior preserved).
- [ ] Built-in provider "Settings" modal still allows adding a model (this path was also broken).
- [ ] No `TypeError` in the browser console on either origin.
- [ ] Unit test passes with `crypto.randomUUID` stubbed to `undefined` (simulating insecure origin).
- [ ] E2E test runs the add-model flow against a non-localhost origin, or the suite gains a documented limitation + unit-level guard.

## 7. Risks & Notes

- **Alternative rejected**: polyfilling `crypto.randomUUID` globally — broader blast radius; the shared helper is narrower and self-documenting.
- The same secure-context trap exists for **any** future use of `crypto.randomUUID`, `crypto.subtle`, etc. Consider a lint rule (`no-restricted-properties`) to catch it at review time.
- Playwright cannot easily run against a LAN IP from CI; a unit test that stubs the API absence is the practical regression guard.
